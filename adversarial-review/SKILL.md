# 독립 리뷰 → Judge → 생산자 응답

적대적 검토는 반례와 실패 조건을 찾는 일이다. 결함 할당량이나 부정적인 결론을 강제하지 않는다. 사용자 목표가 기준이며 Reviewer 수나 Judge의 말이 권한/진실을 결정하지 않는다.

## 실행 계약

착수 시 [references/execution.md](references/execution.md)로 각 단계의 실행 방식을 고른다. 완결된 자료의 판단은 model-only, 조사·재현·수정은 agent가 기본이다. native 추론 호출이 없으면 prompt-only-subagent 대체임을 밝힌다. 역할 분리와 도구 사용 여부를 혼동하지 않는다.

먼저 검토 목적을 구분한다. 명시된 기대의 오류 검수는 기존 findings 흐름을 쓴다. 모호한 기획·품질·대안·세션 평가는 [references/evaluation.md](references/evaluation.md)를 읽고 manifest에 `purpose: evaluation`을 적는다. 두 목적이 섞이면 결함과 비결함 평가를 함께 제출한다. 평가 완료는 사용자 선택 확정이나 제품 품질 승인이 아니다.

1. 사용자 목표·리뷰 대상·제외 범위·허용 수정·검수 기준을 `brief.md`로 고정한다. 대상 파일을 snapshot에 복사하고 원본 경로와 SHA256을 manifest에 남긴다. 기존 기획의 미결정과 코드 관찰을 구분한다.
   모호한 기준은 승인된 합격선으로 고정하지 않는다. 사용자 요구 원문·승인된 결정/이유·리뷰어 제안 기준·미결정을 출처와 함께 나눈다. 리뷰어는 기준 자체가 목적을 충분히 다루는지 점검하며, 제안 기준 변경은 이유와 영향을 드러낸다. 결과에 맞춰 기준을 몰래 바꾸지 않는다.
2. N과 리뷰 관점을 정한다. 미지정이면 작은 파일럿 N=3을 가정으로 알리고 조정 가능하게 둔다. N은 전체 리뷰어 수이며 동시 실행 수와 다르다. 슬롯 부족은 여러 배치로 실행한다. 이번 실행의 상한을 적는다: 기본 첫 리뷰 1회 + 변경/쟁점 재검증 1회. 이는 사용자 영구 예산이나 모든 작업의 고정 횟수가 아니다.
3. 역할별 입력·출력은 [references/contracts.md](references/contracts.md)를 따른다. 실제 요청에 맞게 [references/prompts.md](references/prompts.md)를 채운다. 전체 이전 대화·생산자의 방어 논리·다른 리뷰 결과를 리뷰어에게 상속하지 않는다. 공통 brief/원본과 서로 다른 관점만 준다. 판단 호출에는 경로만이 아니라 실제 필요한 내용을 전달한다. 에이전트를 사용하는 경우 새 subagent는 `fork_turns="none"`; 모델은 환경/사용자가 허용한 설정을 따른다. 같은 모델의 별도 맥락은 다양한 모델 계열의 검증과 다르다.
   설계 이유와 제약을 방어 논리라고 숨기지 않는다. 출처가 있는 공통 사실과 필요한 의존자료를 제공하고, 생산자의 자기평가는 주장으로 표시한다. 부족 자료와 추가 맥락의 공평한 전달은 evaluation.md의 맥락 절차를 따른다.
4. **리뷰어 N명 → 별도 Judge 1명 → 생산자** 순서를 지킨다. 사용자가 사이드바 채팅 생성을 명시한 경우 채팅 도구를 사용한다. 그렇지 않으면 가능한 추론 호출/현재 작업의 subagent를 선택해 채팅을 임의 생성하지 않는다. 판단 전용 호출은 응답만 반환하고 조정자가 원문을 저장한다. 조사 에이전트만 배정된 결과 폴더에 작성한다. 리뷰어/Judge는 대상 수정 금지다. 공유 파일시스템은 보안 격리가 아니므로 소스 해시도 확인한다.
5. 모든 리뷰어 결과를 그대로 Judge에게 준다. 실패한 좌석은 실패로 남겨 재시도/교체/부분 검수 여부를 명시한다. Judge는 원본에 비춰 중복을 묶고 반증·보류·상충 의견을 보존한다. 다수결이나 단일 의견이라는 이유로 지적을 채택/삭제하지 않는다. 생성한 새 지적은 J-new ID와 근거로 분리한다.
6. 생산자는 Judge 결과를 받은 다음 모든 쟁점에 수용/부분 수용/거절/보류와 근거를 작성한다. 수용과 수정 완료는 별개다. 승인된 범위의 수정은 진행하고 코드·검증 증거를 연결한다. 수정 승인 없는 검토라면 제안으로 남긴다. 거절은 반증/비용/범위 근거를 적으며 Judge의 기존 결론을 덮어쓰지 않는다.
7. 같은 Judge 또는 독립 검수자가 변경된 대상과 생산자 응답을 확인한다. 수정 성공은 증거로, 거절은 반증의 타당성으로 평가한다. 미해결 중대 문제·이견·미실행·범위 외 문제는 사용자 보고에 노출한다. 리뷰 규칙 자체를 고쳤다면 이전 고정 기준으로 변경을 판단하고 기준 변경 사실을 별도 밝힌다.
8. 사용자에게 채택/수정·거절·보류·남은 이견·실행한 검증을 보고한다. 일정 상한에 도달해도 합의를 꾸며내거나 자동으로 완료 판정하지 않는다. 새 근거 없이 전체 검토를 반복하지 않는다. 기록은 기존 checkpoint에 연결하고 미래 작업의 상태를 별도 중복 관리하지 않는다.

## 저장과 확인

실행별 폴더: `brief.md`, `manifest.json`, `snapshot/`, `reviews/R1.json...RN.json`, `judge.json`, `producer.json`, `verification.json`, `report.md`. 공통 계약을 각 실행에 복사하지 말고 사용한 버전/해시를 manifest에 포함한다. 파일은 누가 썼는지 명시하되 도구가 역할 신원을 인증한다고 주장하지 않는다.

`scripts/check_review.py <run-directory>`는 모든 리뷰 ID의 Judge 처리, 모든 쟁점의 생산자 응답, 검증 기록 연결과 누락을 검사한다. 검수 의미/증거 진실성은 사람/에이전트 판단이다. 이 도구는 에이전트 호출·게임 실행·수정을 자동 수행하지 않는다. 구조 통과를 제품 승인이나 합의 완료로 쓰지 않는다.

외부 선례와 채택/차이: [references/sources.md](references/sources.md). 전체 외부 플러그인이나 API 서비스를 설치하지 않아도 현재 협업 도구로 수행할 수 있다.
