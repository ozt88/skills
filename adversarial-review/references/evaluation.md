# 목적 부합 평가

계획, 명세, 설계, 아키텍처, 세션 결과가 사용자가 원하는 것을 얼마나 달성하는지 다른 세션이 판정하는 절차다. 작업한 세션은 자기 결과의 옳고 그름을 잘 판정하지 못하고(Huang et al., 2024), 같은 모델은 자기가 쓴 글을 알아보고 더 높게 평가한다(Panickssery et al., 2024). 맥락을 끊는 것만으로는 둘째 문제가 남으므로 아래 장치를 함께 쓴다.

## 목표 고정

- 사용자 목표를 G1, G2처럼 나눠 manifest `goals`에 원문 그대로 적는다. 생산자가 요약한 의도로 대신하지 않는다. 작업한 쪽이 의도를 잘못 옮기면 리뷰 전체가 그 의도를 기준으로 진행된다.
- 리뷰어는 의도가 옳은지가 아니라 대상이 의도를 얼마나 잘 달성하는지를 판정한다. 목표 자체가 사용자 요구와 어긋나 보이면 assessment로 따로 낸다.
- 사용자 명시 요구와 승인된 결정은 출처를 보존한다. 리뷰어가 제안한 대리 지표, 가중치, 성공 문턱은 잠정 기준으로 표시한다. 임의 점수나 장르 관습을 사용자 합의로 승격하지 않는다.
- 판단 근거가 될 원칙 문서가 있으면 snapshot에 넣는다. 프로젝트의 `.knowledge/knowledge/decisions.md`, `guardrails.md`, 설계 원칙 문서가 해당한다. 리뷰어는 지적이 어느 원칙에 닿는지 적는다. 원칙에 없는 기준은 원칙이라고 부르지 않는다.

## 편향 줄이기

- **작성자를 밝히지 않는다.** 대상은 "제출된 안"으로 준다. "내가 작성한", "이 세션에서 만든" 같은 표현과 작성 과정 서술을 지운다. 설계 이유와 제약은 남기되 "작성자 설명"으로 표시한다.
- **기대 조건을 먼저 쓴다.** 리뷰어는 대상을 읽기 전에 목표만 보고, 좋은 안이라면 갖춰야 할 조건과 자기라면 어떻게 접근할지를 `expectations`에 적는다. 그다음 대상을 읽고 대조한다. 조정자는 목표와 원칙을 담은 첫 입력과 대상을 담은 둘째 입력을 나눠 준다. 한 번에 줄 수밖에 없으면 그 사실을 execution.json limits에 적는다.
- **할당량을 두지 않는다.** 결함이나 반론을 최소 몇 개 내라고 요구하지 않는다. 억지 지적은 자기 선호 편향을 반대 방향의 편향으로 바꿀 뿐이다.
- **일치를 독립 확인으로 세지 않는다.** 같은 모델 리뷰어 둘이 같은 지적을 했다고 심각도를 올리지 않는다.

## 렌즈

리뷰어마다 렌즈 하나를 배정한다. 같은 렌즈를 두 좌석에 주지 않는다.

| 렌즈 | 묻는 것 |
|---|---|
| architect | 설계가 명시된 목표에 봉사하는가, 작성자가 가정한 목표에 봉사하는가. 요구가 바뀔 때 어디가 같이 흔들리는가. 책임이 구성 요소 사이로 새는 곳은 어디인가. 규모, 동시성, 순서에 대한 가정 중 먼저 깨질 것은 무엇인가 |
| skeptic | 작성자가 참이라고 믿지만 증명되지 않은 것은 무엇인가. 어떤 입력, 상태, 순서에서 계획이 무너지는가. 실패 경로와 되돌리는 방법은 정해져 있는가. 확인했다는 말이 실제 확인인가 |
| minimalist | 목표를 잃지 않고 무엇을 지울 수 있는가. 아직 없는 문제를 푸는 곳은 어디인가. 두 번째 사용처 없이 추가한 유연성은 무엇인가. 가장 단순한 길인가, 가장 철저해 보이는 길인가 |

minimalist는 대상의 절이나 구성 요소마다 "이것을 빼면 어느 목표가 깨지는가"를 `removals`에 적는다. 어느 목표에도 닿지 않는 요소는 과설계 후보다. 목표 달성표가 목표에서 대상을 보는 검사라면, 빼 보기는 대상에서 목표를 보는 검사다.

brief가 다른 렌즈를 정의해도 된다. 그때는 렌즈 이름과 질문을 brief에 적는다.

## 규모와 N

| 대상 | N | 렌즈 |
|---|---|---|
| 결정 하나, 한두 쪽 분량 | 1 | architect |
| 여러 결정이 얽힌 명세나 계획 | 2 | architect, skeptic |
| 시스템 아키텍처, 되돌리기 어려운 결정, 긴 명세 | 3 | architect, skeptic, minimalist |

N=1이어도 Judge와 검증은 별도 좌석으로 둔다. 사용자가 N을 정했으면 그것을 따른다.

## 판단의 연결

관측 사실 → 해석과 조건 → 선택지와 보존할 장점 → 모르는 점 → 다음 행동을 잇는다. 결함이 없어도 유용한 평가다. 자료가 부족하면 무엇을 보면 어떤 판단을 할 수 있는지까지 적는다. 실제 이미지 없이 시각 품질을 판정하지 않는다. 사용자가 결정할 가치나 취향만 질문으로 남기고, 파일 조사와 비교 준비는 승인 범위에서 계속한다.

세션 평가는 공개된 사용자 요구, 선택과 결정 기록, 산출물, 시험, 완료 주장을 대상으로 한다. 비공개 사고를 요구하거나 의도를 추정하지 않는다. 작업이 덜 끝난 것과 중간 작업이 목적에서 벗어난 것을 구분한다.

## 공통 맥락과 추가 자료

공통 brief에 질문과 원문 출처, 승인된 제약과 이유, 잠정 기준, 미결정, 대상과 의존 자료의 위치, 관측 가능한 증거와 빠진 자료를 적는다. 필요한 맥락이 파일에 있으면 먼저 찾는다. 생산자의 선별 요약으로 승인 사실을 대신하지 않는다. 읽지 않은 자료를 읽었다고 전제하지 않는다.

각 리뷰어는 시작할 때 평가할 수 있는 부분과 자료가 부족한 부분을 요약한다. 추가 요청은 자신의 결과 폴더에 남기고 조정자에게 보낸다. 조정자는 사실, 출처, 미확인을 담은 답을 `context-updates.md`에 버전을 붙여 남기고 모든 리뷰어와 Judge에게 같은 내용으로 전한다. 다른 리뷰어의 결론은 공유하지 않는다. 이미 제출한 검토에 영향을 주면 해당 부분의 보충 의견을 요청하고 기존 제출은 보존한다. 다시 실행하지 못한 좌석은 이전 맥락 버전임을 표시한다. 자료가 없는 부분만 보류하고 나머지 평가는 계속한다.

## 비결함 판단의 전달 계약

기존 역할 JSON에 배열을 넣는다. 파일을 늘리지 않는다.

- Reviewer `assessments`: 각 항목 `id`(R1-E01), `question`, `criteria`(문장 배열, 각 기준의 출처와 확정, 제안, 미정 여부), `observation`, `interpretation`, `unknowns`(문장 배열), `next_action`, `goal_ids`(다루는 목표, 선택). 장점과 조건별 대안은 interpretation에 담는다. P등급을 붙이지 않는다.
- Judge `assessments`: 각 항목 `id`(A-001), `source_ids`(리뷰어 평가 ID), `conclusion`, `reason`, `next_action`, `decision_owner`(user/producer/none), `evidence` 배열. 모든 평가를 정확히 한 항목에 연결하며 통합, 보류, 제외의 이유를 남긴다. 사용자 판단을 대신 확정하지 않는다. 서로 모순되는 해석은 조건과 함께 보존한다.
- Judge `goal_attainment`: contracts.md 참고. 리뷰어의 expectations와 대상의 차이가 판정의 주된 근거다.
- Producer `assessment_responses`: 각 항목 `assessment_id`, `action`, `reason`, `evidence`. 다음 행동을 수행했는지, 제안으로 남겼는지, 사용자 선택을 기다리는지 구분한다. Judge 결론을 지우지 않는다.
- Verifier `assessment_results`: 각 항목 `assessment_id`, `status`(documented/open/decision-needed/not-run), `reason`, `evidence`. documented는 평가와 응답이 제대로 기록됐다는 뜻이며 선택이나 품질 승인, 후속 구현 완료가 아니다. decision-needed는 사용자 선택이 남은 상태다.

검사기는 연결 누락만 확인한다. `pending_assessments`, `failed_reviewers`, `overdesign_candidates`, unmet 목표를 사용자 보고에서 숨기지 않는다. 평가를 많이 만들었거나 전원이 동의했다는 것만으로 의미 있는 결과라고 하지 않는다.

## 유용성 판단과 비용

최종 보고에 목표별 달성 상태, 이번 평가로 분명해진 선택 조건, 고친 주장과 결함, 유지한 장점, 다음에 확인할 관측을 적는다. 기존 판단을 그대로 확인한 경우도 구분한다. 실제 채택, 수정, 실행 결과와 아직 제안인 것을 나눈다. 검토 비용은 알 수 있는 범위에서 기록하고, 시간이나 토큰을 재지 않았으면 추정 수치를 만들지 않는다. 작은 정상 수정은 추가 변경 없이 끝낼 수 있다.

사례 시험에서 추가 지시나 잘 정리된 합성 자료가 도왔으면 그 기여를 밝힌다. Reviewer 단계만 수행했으면 전체 절차를 검증했다고 부르지 않는다. 전후 비교나 대조군 없는 시험으로 일반적인 생산성 향상을 주장하지 않는다.
