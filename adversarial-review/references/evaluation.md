# 기준이 모호한 작업의 평가

## 목적과 기준

평가 질문을 먼저 적는다. 재미/읽기 쉬움/설계 적합성/완료 판단에는 여러 평가 축이 있을 수 있다. 사용자 명시 요구와 승인된 결정은 출처를 보존하고, 리뷰어가 제안한 대리 지표·가중치·성공 문턱은 잠정 기준이라고 표시한다. 임의 점수나 장르 관습을 사용자 합의로 승격하지 않는다. 명확한 코드 기대에는 기준 발굴 문서를 추가하지 않는다.

리뷰어는 생산자가 정한 기준이 목적의 일부만 다루는지 검토한다. 예를 들어 자동화의 시간 절약과 반복 입력 해방은 다른 효용이다. 우선순위가 미정이면 조건별 결론과 작은 판별 실험을 제시한다. 정량 지표가 없다는 이유만으로 평가를 포기하거나 정량 점수를 발명하지 않는다.

관측 사실 → 해석/조건 → 선택지·보존할 장점 → 모르는 점 → 다음 행동을 연결한다. 결함이 없어도 유용한 평가다. 자료 부족은 무엇을 보면 어떤 판단을 할 수 있는지까지 구체화한다. 실제 이미지 없이 시각 품질을 판정하지 않는다. 사용자가 결정할 가치/취향만 질문으로 남기고 파일 조사·비교 준비는 승인 범위에서 계속한다.

세션 평가는 공개된 사용자 요구·선택/결정 기록·산출물·시험·완료 주장을 대상으로 한다. 비공개 사고를 요구하거나 의도를 추정하지 않는다. 작업이 미완료인 것과 중간 작업 자체가 목적에서 벗어난 것을 구분한다. 외부 리뷰가 자기평가보다 낫다는 일반 명제는 별도 비교 없이는 주장하지 않는다.

## 공통 맥락과 추가 자료

공통 brief에 질문/원문 출처, 승인된 제약과 이유, 잠정 기준, 미결정, 대상/의존자료의 위치, 관측 가능한 증거와 빠진 자료를 적는다. 필요한 맥락이 파일에 있으면 먼저 찾는다. 생산자의 선별 요약만으로 승인 사실을 대신하지 않는다. 읽지 않은 자료를 읽었다고 전제하지 않는다.

각 리뷰어는 시작 시 평가 가능한 부분/자료가 부족한 부분을 요약한다. 추가 요청은 자신의 결과 폴더에 남기고 조정자에게 보낸다. 조정자는 사실·출처·미확인을 담은 답을 `context-updates.md`의 버전으로 남겨 모든 리뷰어와 Judge에게 같은 내용으로 전달한다. 다른 리뷰어의 결론은 공유하지 않는다. 이미 제출한 검토에 영향을 주면 해당 부분의 보충 의견을 요청하고, 기존 제출은 보존한다. 재실행 못한 좌석은 이전 맥락 버전임을 표시한다. 자료가 없는 부분만 보류하며 나머지 평가를 계속한다.

## 비결함 판단의 전달 계약

`purpose: evaluation`인 실행은 결함 유무와 별개로 아래 경로를 쓴다. 파일 수를 추가하지 않고 기존 역할 JSON에 배열을 넣는다. 코드 결함만 검수하는 실행은 생략 가능하다.

- Reviewer `assessments`: 각 항목 `id`(R1-E01), `question`, `criteria`(문장 배열; 각 기준의 출처·확정/제안/미정을 적음), `observation`, `interpretation`, `unknowns`(문장 배열), `next_action`. 장점·조건별 대안은 interpretation에 담는다. P등급을 부여하지 않는다.
- Judge `assessments`: `id`(A-001), `source_ids`(Reviewer 평가 ID), `conclusion`, `reason`, `next_action`, `decision_owner`(user/producer/none), `evidence` 배열. 모든 평가를 정확히 한 항목에 연결하며 통합·보류·제외의 이유를 남긴다. 사용자 판단을 대신 확정하지 않는다. 서로 모순되는 해석은 조건과 함께 보존한다.
- Producer `assessment_responses`: `assessment_id`, `action`, `reason`, `evidence`. 다음 행동을 수행했는지, 제안으로 남겼는지, 사용자 선택을 기다리는지 구분한다. Judge 결론을 삭제하지 않는다.
- Verifier `assessment_results`: `assessment_id`, `status`(documented/open/decision-needed/not-run), `reason`, `evidence`. documented는 평가/응답이 적절히 기록됐다는 뜻이며 선택/품질 승인이나 후속 구현 완료가 아니다. decision-needed는 실제 사용자 선택이 남은 상태다.

검사기는 연결 누락만 확인한다. `pending_assessments`와 `failed_reviewers`를 사용자 보고에서 숨기지 않는다. 단순히 평가를 많이 생성하거나 전원 동의했다고 유의미한 결과라고 하지 않는다.

## 유용성 판단과 비용

최종 보고에 이번 평가로 명확해진 선택 조건, 수정한 주장/결함, 유지한 장점, 다음에 확인할 관측을 구체적으로 적는다. 기존 판단을 그대로 확인한 경우도 구분한다. 실제 채택·수정·플레이 결과와 아직 제안인 것을 나눈다. 검토 비용은 알 수 있는 범위에서 기록하고 시간/토큰 미측정이면 추정 수치를 만들지 않는다. 작은 정상 수정은 추가 변경 없이 종료할 수 있다.

사례 시험의 추가 지시나 잘 정리된 합성 자료가 도왔으면 그 기여를 공개한다. 사례의 Reviewer 단계만 수행했으면 전체 N/Judge 절차를 각 사례에 검증했다고 부르지 않는다. 전후/대조군 없는 시험으로 일반적인 생산성 향상을 주장하지 않는다.
